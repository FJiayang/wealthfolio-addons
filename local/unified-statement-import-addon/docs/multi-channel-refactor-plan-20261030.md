# unified-statement-import-addon 多渠道重构方案

> 基于 ezbookkeeping（下称 [ezB]）与 double-entry-generator（下称 [DEG]，本地 deb-sig
> fork v2）两项目的源码分析，结合本插件现状，2026-10-30。
> 渠道规则条目均摘自两个项目的真实源码与测试，标注来源；`file:line`
> 引用指向各自仓库。四态行、`source.system` 不变量、来源身份、错误分级、银行公共规则
> 是本插件基于源码事实做出的设计约束，不是对方已有实现。
>
> 2026-10-30 修订：校正字段/列数、金额类型、招行跨年、工行双列、美团/随手记枚举、支付宝变体、
> DEG 退款识别、中信/浦发示例等事实错误；补充 `source.system` 不变量、四态行、来源身份、
> 错误分级、银行公共规则，以及建行/中行/农行/交行/广发/兴业购汇合并等渠道规则。

## 0. 结论速览

1. **本插件骨架是对的，不用推倒**：注册表 + 表头探测分发、四层（行级指纹冲突 → 批内 seen → 跨文件来源索引 → 提交签名恢复）去重、会话幂等、决策合并已经是两个开源项目都没有的能力（ezB 无账单行级去重、DEG 无幂等）。重构 = 保留骨架 + 解除 12 个硬编码点 + 吸收两家的渠道知识。
2. **两个项目最值得抄的三件事**：
   - [ezB] 语义列中间模型（parser 只产出 canonical 字段 map，UI/记账层不感知渠道）
   - [ezB] 行级结果状态（valid / invalid / error 三路）；本插件应扩展为四态：`ok / softSkip / hardSkip / fatal`，其中 `softSkip` 对应现有「不计收支默认排除但用户可恢复」，不能退化成不可恢复的 skip
   - [DEG] 账户映射规则引擎（多规则累积、contains/fullMatch、方向自动交换、FIXME 兜底）
3. **两个项目都没做、你可以超车的**：账单头部统计对账（共 N 笔 / 收入合计 / 支出合计 vs 解析结果）、可恢复的行级错误（DEG 在 analyser 中使用 `log.Fatalf`，GUI 语境不可接受）。
4. **渠道别贪多**：支付宝自身就有 3 种导出变体，微信 2 种格式。**P1 先做微信 + 一家银行（招行借记）**，把「同渠道多变体」的抽象磨稳再铺开。注意：微信 `/` 转账行在 transfer 支持（P3）前必须进 review/softSkip，不能当收入或支出导入。
5. **天天基金属投资类账单，两个项目都不覆盖**，建议走仓库已有的蚂蚁基金插件
   `activities.openImport()` 托管路线，不要塞进本插件。交接后宿主负责资产识别、重复处理和持久化，插件 metadata/来源指纹**不一定保留**，不能假设宿主按本插件 `sourceKey` 去重。

## 2. 重构不得破坏的本插件强项

1. **四层去重**：行级指纹冲突 → 批内 seen
   → 跨文件（`metadata.unifiedStatementImport.sources`
   索引，`sourceKey = [system, recordId]`）→ 提交签名比对 + 失败重读恢复（`session.ts`）。
   **前提不变量**：`system` 必须是稳定的**渠道 id**（`alipay` / `wechat` / `ccb`），
   不是导出变体 id（`alipay-app` / `alipay-web`）。同一渠道的不同变体必须共享
   `system`，否则同一订单在 app/web/回单之间会重复导入，且
   `getStatementParser(source.system)` 会找不到 parser。
2. **测试方法论**：合成 fixture（不入库真实账单）、表驱动 18 家银行别名测试、`STATEMENT_DEMO_PATH`
   / `STATEMENT_TEST_ORIGIN` 环境变量门控验收。
3. **决策体系**：`RowDecision`（按 lineNumber 键控）+ 优先级 decisions > saved
   mapping > inference。
4. **metadata v1**：版本严格校验，未知版本阻断不静默（`ledger.ts:59-94`）。
5. **金额全程字符串**。

## 3. 架构重构方案

### 3.1 分层目标

分层从文件字节到提交，顺序固定：

1. **读取层**：参数化编码、分隔符、BOM；由渠道档案供稿。
2. **语法层**：CSV/XLSX 解析，保留物理行号。
3. **渠道层**：header 签名、列映射、日期、金额、状态语义；唯一渠道知识所在地。
4. **四态行**：`ok` / `softSkip` / `hardSkip` / `fatal`。
5. **中间模型**：canonical 语义列，渠道中性。
6. **账户映射**：规则引擎 + 推断 + 用户映射。
7. **preview / decisions / submit**：全部保留现状。

渠道知识优先写成档案数据；只有无法声明化的部分（支付宝商品说明分支树、微信服务费、
银行可选列/借贷标志探测）才允许提供 row hook。**如果每个变体都实现完整解析函数，
档案字段就形同虚设，重构只是把硬编码换了个文件。**

### 3.2 核心接口（字段说明）

**StatementParser（渠道级）**

| 字段 | 含义 |
| --- | --- |
| `id` | 渠道身份：`alipay` / `wechat` / `ccb`；写入 `source.system`，不可变 |
| `displayName` | 界面名称 |
| `variants` | 同渠道多导出变体（支付宝 3 种、微信 2 种） |
| `previewColumns` | 上传预览列：StatementSource 字段 + 显示标签，消除页面硬编码 |
| `categoryLabel` | 可选；支付宝用「支付宝分类：」，其他渠道省略 |
| `uploadLabel` / `fileHint` / `mappingHint` / `recordIdLabel` / `formats` | 现有字段，保留 |

**ParserVariant（变体级）**

| 字段 | 含义 |
| --- | --- |
| `id` | 变体 id（`alipay-app-csv` 等），只用于内部选择和展示，不写入来源身份 |
| `headerSignatures` | 多候选文件头/表头签名，抗渠道主体名漂移（电子回单双主体名） |
| `requiredColumns` / `optionalColumns` | 列名集合匹配，列序无关；可选列缺失时填空（招行借记） |
| `encoding` / `stripBom` / `delimiter` / `trimFields` | 编码列表、BOM 剥离、分隔符、字段 trim |
| `skipLeadingRows` | 仅作无法定位表头时的兜底，优先用锚点 |
| `stopWhen` | 页脚/合计行停止条件（列号 + 等值/包含） |
| `columns` | 原始列到标准字段的映射：时间、类型、金额、状态、方式、对方、单号等 |
| `timestamp` | `formats` 按顺序尝试；`zone` 固定 `Asia/Shanghai`；`dateOnlyTime` 决定日期-only 落点；`yearFromStatement` 从账单标题取年月；`fallbackColumn` 用记账日兜底交易日 |
| `amount` | `thousandSeparator`、`decimalSeparator`、`currencyAffixes`、`unitScale`（1 或 100）、`sign`（as-is / invert）、`columns`（收入/支出双列）、`stripParensNote`（退款括号注记） |
| `semantics` | 方向映射（含 ignore）、成功状态、退款状态、排除状态、默认排除方向 |
| `rowHook` | 仅特殊渠道：支付宝商品说明分支树、微信服务费、银行可选列/借贷标志探测 |

**ParsedRow（四态）**

| kind | 必填 | 含义与 UI |
| --- | --- | --- |
| `ok` | `fileName`、`lineNumber`、`row`，可选 `typed` | 可提交；`typed` 保存渠道归一后的类型 |
| `softSkip` | `fileName`、`lineNumber`、`reason`，可选 `row` | 默认跳过但可恢复（不计收支、用户临时排除） |
| `hardSkip` | `fileName`、`lineNumber`、`reason`，可选 `row` | 不可恢复（交易关闭、明确排除状态），计数展示 |
| `fatal` | `fileName`、`lineNumber`、`cause`，可选 `column` / `raw` | 行级错误，必须修正或删除后才能提交 |

要点：

- **读取层由档案供稿**，不再全局固定：这是银行渠道阻塞点的解除方式（现有
  `csv.ts` 的分隔符/日期/金额/编码 4 个全局假设）。
- **`softSkip` 必须保留**：现有「不计收支」是默认排除但用户可恢复（`defaultExcluded`），不能退化成不可恢复的 `hardSkip`。`hardSkip` 只用于交易关闭、非法行等不可恢复项。
- **skip 行要计数透出**（「已跳过 N 行：交易关闭 12、不计收支 3、无法归类 2」），不静默——ezB 是日志 warn，GUI 里要可见。
- **解析函数不是每个变体的必填项**：通用引擎先按读取、列映射、日期、金额、状态语义解析；只有支付宝商品说明分支树、微信服务费、银行可选列探测等无法声明化的逻辑才用 row hook。否则档案字段不会真正生效。
- 金额沿用字符串算术（现有 `normalizeAmount`
  扩展参数：允许负号、多位小数、千分位、货币前后缀、剥括号注记、分单位换算）。
- **`source.system` 只写 `StatementParser.id`**，变体 id 永不进入来源身份；这是跨变体去重和 `getStatementParser(source.system)` 的前提（详见 §3.8）。

### 3.4 转账支持（微信/银行的最大语义缺口）

ezB 明确把「不计收支 / `/`」当作转账/调账入口；DEG 把这些方向映射为
`ir.TypeUnknown`，再由 analyser 规则决定资产/负债账户，**不会自动生成双分录转账**。
两者的关键词分支：

- 支付宝「不计收支」分支树（ezB
  `alipay_transaction_data_row_parser.go:122-188`）：
  - `商品说明` 以 `-收益发放` 结尾 → income（理财收益）
  - `-买入` / `-买入退款` / `-卖出` → transfer（理财申赎）
  - `充值-` / `提现-` 前缀 → 余额转入/转出
  - 含 `转入/转出/转账/还款` → transfer；全部不匹配 → review
- 微信 `/` 分支：`零钱充值`→transfer、`零钱提现`→transfer、`信用卡还款`→transfer
  （ezB 特判为调账）；都不匹配 → ezB 为 fatal，DEG 可 `--ignore-invalid-tx-types` 降级 WARN。
  本插件应降级为 **review**，不要抄 fatal。

**宿主侧现状（SDK `host-api.ts`）**：

- `activities.saveMany` 负责活动写入；`saveTransferPair` 创建或更新一对内部转账；
  `linkTransfer(a,b)` 把两条**已存在**活动连成转账；`unlinkTransfer` 解除。
- `saveMany` 与转账 API 是两次调用，**不能原子组合**；update/link 的失败恢复沿用现有 uncertain 流程。
- 用 `saveTransferPair` 的**创建模式**（不传 leg ids）会新建两条活动；
  如果一期已经创建了两条腿，二期应调用 **`linkTransfer`**，或传两个 leg ids 更新，
  否则会重复记账。

分两期落地：

- **一期（transfer 支持落地时，P2 末/P3）**：单边转账行只创建已知的一侧，**不虚构对手方**。
  - 若宿主允许未配对的 `TRANSFER_OUT` / `TRANSFER_IN`，直接创建并写
    `metadata.pendingTransfer`；否则降级为 `WITHDRAWAL` / `DEPOSIT` + 同一 metadata，
    UI 明确标注「待配对」，不宣称是内部转账。
  - 若账单本身含两条腿（如随手记按 `关联Id` 配对），创建两条后立即
    `linkTransfer`；失败进入既有的不确定结果恢复。
  - 转账行在对手方确认前保持 review/分组成员，不自动提交。
- **二期（P3）**：用户映射对手方或导入另一份账单后，用
  `linkTransfer(existingOut, existingIn)` 补配对；只有缺失腿需要新建时才用
  `saveTransferPair` 创建模式。metadata 状态机 `pendingTransfer → linked`，
  失败可重试、可查询，复用现有「uncertain 恢复」。
- **P1 微信门禁**：transfer 支持落地前，微信 `/` 行一律 review/softSkip 并计数，
  **绝不能当收入或支出导入**；否则 P1 的“支持微信”是假完成。

**数据结构影响**：PreviewRow 目前假设一行对应一个活动创建对象，要改为一行可对应多个活动（或一个待配对占位）。批内 seen 仍按**来源行**键控，不能让两条腿互相判重；提交计数要区分「行数」与「活动数」。

### 3.5 账户映射升级（DEG 规则引擎语义移植）

现有打分推断保留；在 saved
mapping 与 inference 之间插一层**用户可编辑规则**（持久化进 `storage`）：

| 字段 | 含义 |
| --- | --- |
| `id` / `enabled` | 规则标识与开关 |
| `matchMode` | `all` 或 `any`；默认 `all`：同一规则内字段 AND，多条规则之间 OR |
| `match` | 匹配条件列表：字段（`method` / `peer` / `item` / `category` / `txType`）+ `contains` / `equals` + 可选 `sep`（多关键词 OR，默认 `,`） |
| `timeRange` | 时间段，如 `11:00-14:00`（对应 DEG `time`） |
| `minAmount` / `maxAmount` | 金额区间（对应 DEG `minPrice` / `maxPrice`） |
| `direction` | `income` / `expense` / `transfer` |
| `targetAccountId` | 目的账户；与 `methodAccountId` 至少给一个 |
| `methodAccountId` | 资金/对方账户 |
| `ignore` | 黑名单，防跨渠道重复记账 |
| `priority` | 规则排序；数值越大越先应用 |

- **匹配语义**：同一规则内按 `matchMode` 做 AND/ANY；多条规则按 `priority` 排序后逐条应用。
- **冲突语义**：同一侧账户以**最后命中的规则**为准；`ignore` 命中即短路（DEG `pkg/analyser/alipay/alipay.go` 的 `if r.Ignore { ignore = true; break }`）。
- **方向交换**：`targetAccountId` 在收入时写 minus、支出时写 plus；`methodAccountId` 相反——直接复用 DEG `pkg/analyser/alipay/alipay.go:116-129` 的 Recv/Send 交换逻辑；退款在 analyser 末尾还有一次 swap，别漏。
- 规则匹配原语抄 DEG
  `pkg/util/util.go:10-34`：`SplitFindContains`（多关键词 OR，分隔符默认 `,`）/
  `SplitFindEquals`（全等）。
- **method 先归一化再匹配**：复用 `normalizeInstrument()`，避免「招行」「招商银行」「招行信用卡(1234)」各存一条规则；原始字符串只用于展示。
- **未匹配兜底**：不明确的行保持现有 review 分组，但补「按未匹配原因批量重指派」（一键把 N 行「零钱」全部指到某账户）——比 DEG 的
  `Assets:FIXME` 文本约定更适合 GUI。

### 3.6 头部统计对账（两家都没做，超车点）

支付宝交易明细头部有「共 N 笔记录」（部分导出还有收入/支出合计）；浦发尾部是「合计」，兴业尾部是「说明」，建行是「以上数据仅供参考」，工行是「合计金额/人民币合计」。建议 parser 在档案声明
`summaryExtract`（正则组），提取后与解析结果核对：

- **源声明行数**（头部/尾部统计）
- **解析条数**（`ok + softSkip + hardSkip + fatal`）
- **可提交条数**（`ok` 中最终能写入的）
- **金额合计**（按方向分别求和）

不一致时给 warning（不阻断，头部统计经常对不上是渠道自身 bug），显示在 result 页：「源声明 66 笔 / 解析 64 笔 / 软跳过 1 笔（不计收支）/ 硬跳过 1 笔（交易关闭）/ 可提交 62 笔」，用户可滚动差异行。不要用头部数字覆盖或丢弃明细。

### 3.7 UI 由档案驱动

- 上传预览列 = `parser.previewColumns`；固定映射说明 = 档案文案。
- 结果汇总卡分别显示 `softSkip / hardSkip / fatal` 的数量与原因分布；`softSkip` 保留现有「恢复」入口。
- 1301 行的 `statement-import-page.tsx` 拆分：`useImportWizard()`
  hook（状态机）+ 各步骤小组件（每个 <400 行）。`@wealthfolio/import-wizard-ui`
  继续复用。

### 3.8 来源身份与去重不变量

这一节是 P1 前必须定稿的硬约束，否则多渠道会重复记账。

1. **渠道身份**：`source.system = StatementParser.id`，变体 id 不写入来源。
   支付宝 app/网页/电子回单三种导出共享 `system: "alipay"`。
2. **记录身份**：`sourceKey = [system, identity]`，`identity` 由 profile 声明：
   - 支付宝：`交易订单号`；缺失时 `商家订单号` 可作辅助，但仍需 review。
   - 微信：`交易单号`；`商户单号` 辅助。
   - 京东/美团：交易单号 + 商家单号。
   - 银行：优先 `流水号/交易流水号`；没有时用 profile 声明的复合键
     `[日期, 金额, 方向, 余额, 对方账号]`，生成**确定性** `composite:` 哈希。
     复合键字段不足或可能重复时进入 review，**不允许随机 UUID 冒充订单号**。
3. **跨变体**：同一渠道的不同导出必须命中同一 `sourceKey`，不得因文件头/列名不同而重复。
4. **跨文件**：`fileName + lineNumber` 只用于定位，不参与身份；同一订单出现在两个文件中仍应判重。
5. **跨来源**：`sources[]` 结构允许追加，但本版仍只写一个 source。后续跨源关联只做候选预览：
   相同已映射账户、币种、金额、方向且参考号精确一致且唯一时才自动关联；日期/金额相近只能人工确认。
6. **metadata v1 兼容**：新增可选 source 字段（如 `peerAccount`）不升版本；读取旧数据缺字段照常工作。
   未知版本、损坏结构继续阻断提交，不静默忽略。

### 3.9 错误分级策略

| 级别 | 使用场景 | UI/提交行为 |
| --- | --- | --- |
| `fatal`（文件级） | 无法解码、找不到表头、缺必需列、重复列、没有数据行 | 停止该文件，不进入映射 |
| `fatal`（行级） | 列数与表头不符、金额/日期无法解析 | 该行标红，必须修正或删除后才能提交 |
| `review` | 未知交易状态/类型、未知转账说明、缺少订单号、零金额、账户未定 | 进入待确认分组，用户可逐行/批量确认或跳过 |
| `softSkip` | 「不计收支」默认跳过、用户临时排除 | 计数展示，可恢复；恢复后须补齐性质/金额/账户 |
| `hardSkip` | 交易关闭、明确排除状态 | 计数展示，不可恢复 |

**未知业务值一律 review，不抄 DEG 的 `log.Fatalf` / ezB 的整行 fatal。**
`fatal` 只用于结构性问题；状态/类型枚举随渠道升级会不断出现新值，不能因此阻断整份账单。
同一行有多个问题时全部列出，不要只报第一个。

## 4. 渠道解析档案库（第一手规则，两项目源码摘录）

> 使用方式：P1+ 每接入一个渠道，对照本节条目实现 + 用「golden 测试」（§5）固化。
> 共性事实：header 探测一律用签名/Term 特征而**不要硬编码跳行数**（DEG 跳 22/17/21 行是反面教材，支付宝换版即崩）。

### 4.0 银行公共规则（先定这套，再看单家差异）

1. **文件与编码**：银行 CSV 常见 GBK/GB18030，Excel 常见 XLS/XLSX；先按 BOM/表头判断，不要默认 UTF-8。
2. **边界**：银行文件通常有标题行、账户信息行、表头行、数据行、合计/说明页脚。优先用「文件头关键词 → 数据表头关键词 → 页脚关键词」状态机；分页会重复表头，必须按内容跳过。
3. **列映射**：有表头的按列名取；**可选列缺失时填空，不要按固定列序硬读**（招行借记是典型）。只有明确不支持表头重排的 provider（如浦发）才按固定列序读，并在文档里写明。
4. **金额形态**：
   - 单列带符号：负 = 支出（借记卡）或负 = 收入（信用卡，符号反转）。
   - 双列收入/支出：一列非空定方向；两列都非空先取净额，净额为 0 再看摘要；两列都为 0 按摘要/查询行处理。
   - 借贷标志：`借` = 支出、`贷` = 收入（交行）。
   - 金额列可能带千分位、货币符号、括号注记；先清洗再转精确字符串。
5. **日期**：支持 `YYYY-MM-DD`、`YYYYMMDD`、`YYYY/MM/DD`、`YYYY-MM-DD HH:mm:ss`；只有日期的用固定 `dateOnlyTime`；信用卡只有 `MM/DD` 时从账单标题取年月，并处理跨年；交易日缺失时用记账日兜底。
6. **方向语义**：银行多数没有「状态」列，`摘要/交易类型/借贷标志` 才是语义来源；「查询/余额」行、0 金额行、挂失费等不产生资金流动的行应 hardSkip。
7. **账户识别**：账户名/卡号/末四位可能在文件头、列值或摘要里；profile 声明 `accountHint` 的提取方式，不要把摘要里的任意数字当卡号。
8. **身份与去重**：银行普遍没有支付宝式订单号。优先 `流水号`；否则用 `日期+金额+方向+余额+对方账号` 的确定性复合键；字段不足时 review，不得随机生成 ID。
9. **多币种**：兴业等存在「购汇/结汇」一出一进；同一账号、同一摘要、不同币种、时间差 ≤ 3 分钟可合并为 CurrencyExchange，否则按两条外币流水导入并 review。
10. **失败策略**：未知摘要/未知借贷标志 → review；缺列/列数不符 → 行级 fatal；找不到表头 → 文件级 fatal；页脚缺失不阻断。

### 4.1 支付宝（3 种变体）

|     | 变体                       | 关键差异                                                                                                                                                              |
| --- | -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A   | 交易明细导出（当前插件）   | 文件头 `支付宝账户：xxx` + `共 N 笔记录`；12 列：`交易时间/交易分类/交易对方/对方账号/商品说明/收/支/金额/收/付款方式/交易状态/交易订单号/商家订单号/备注`；9 必需列。**此变体不在 ezB 的 `alipayApp`/`alipayWeb` 测试中**，不要标 `[ezB]` |
| B   | 网页交易记录查询           | 文件头 `支付宝交易记录明细查询`，数据起点 `----交易记录明细列表----`；列：`交易创建时间/交易对方?/商品名称?/金额（元）/收/支/交易状态/备注`；**无「交易分类」、无「收/付款方式」**；`交易对方`/`商品名称` 可选 [ezB] |
| C   | 电子客户回单               | 文件头 `支付宝账户：xxx` + `...电子客户回单...`；主体签名双候选（支付宝中国/支付宝支付科技）；列与 A 接近。DEG 的 provider 变体跳 22 行、GBK、固定 11 列，老版（≤1.7.0）直接报错引导重导 |

- **编码**：GB18030 覆盖 GBK 生僻字 [ezB]；A/C 也可能是 UTF-8；字段 trimSpace（列对齐空格）[ezB]
- **收/支列**：`收入/支出/不计收支`；「不计收支」→ §3.4 分支树
- **状态识别白名单**（两项目并集）：`交易成功/支付成功/代付成功/解冻成功/还款成功/等待确认收货/交易关闭/已关闭/退款成功/退税成功/芝麻免押下单成功`
- **关闭**：ezB 对「收入」和「不计收支」的关闭行静默跳过；对「支出」关闭行没有跳过（源码缺口）。本插件统一排除所有 `交易关闭/已关闭`，计入 `hardSkip`，不导入。
- **退款**：
  - 现插件：`退款成功` + 非支出方向 → `kind: refund`（宿主 `CREDIT` + `subtype: REFUND`）；支出方向退款保持 `expense` + review。
  - ezB：收入退款用负金额翻转成支出。
  - DEG：仅支付宝 provider 识别「状态为退款成功且分类为退款」，再用**退款订单号前缀 + 金额相等**找原交易，两笔都标记 `useless`（除非 `keepRefundRecords`）。这是“账本对冲”，**不要照抄成删除**；本插件保留每笔来源，按 `sourceKey` 去重。
- **转账/理财**：`商品说明` 分支树见 §3.4；注意 `-卖出` 在源码里是 **contains** 匹配，不是严格后缀。
- **对方账号**：`对方账号` 可用于增强尾号/账户匹配（现插件未读）；作为可选 source 字段加入，不算 metadata 版本升级。
- **页脚**：电子回单/部分导出底部有全 `-` 分隔线（「共 N 笔」通常在头部）；profile 用 `stopWhen` 截断，不能把页脚当数据行。

### 4.2 微信支付（CSV / XLSX 双格式）

- **探测**：header 签名「微信支付账单明细」+ 分隔线行
  `------…------微信支付账单明细列表------…` [ezB]
- **编码**：UTF-8 带 BOM（`BOMOverride`）[ezB]；`unicode.BOMOverride` 也会识别 UTF-16 BOM，encoding 列表保留兜底。
- **结构**：头部有若干行元数据（昵称/起止/笔数）；CSV 与 XLSX 行数不同，**不要抄 DEG 的 17/18 行硬编码**，用锚点。
- **列**：`交易时间/交易类型/交易对方/商品/收/支/金额(元)/支付方式/当前状态/交易单号/商户单号/备注`
- **空值哨兵是 `/` 不是空串**：备注 `"" 或 "/"` 皆视为无；**只有收入分支**把空/`/` 支付方式映射到微信钱包。转账分支用原始值，`/` 不代表零钱。
- **收/支列**：`收入 / 支出 / /`（斜杠=中性）[ezB]
- **金额**：`￥1,234.56` —— 删千分位 + 取第一个连续数字串（剥货币符号）[ezB]；不要用浮点。
- **交易类型 19 枚**（DEG Contains 链，顺序影响匹配）：
  `商户消费/微信红包/转账/二维码收款/扫二维码付款/群收款/退款/转入零钱通-来自零钱/转入零钱通/零钱充值/零钱提现/信用卡还款/购买理财通/零钱通转出-到零钱/零钱通转出/亲属卡交易/赞赏码/其他/分分捐`。
  未知类型本插件记 **review**，不要抄 DEG 的 fatal。
- **硬规则**：`零钱提现` 强制改收入方向 [DEG]；备注含「服务费」→ 正则 `\d+\.\d{2}` 取第一笔、从主金额扣除、commission 单独入账；DEG analyser 在未配置 `defaultCommissionAccount` 时会 `log.Fatalf`，本插件应改为 review/提示选择手续费账户。`信用卡还款` 在 ezB 中映射为「账户=支付方式、对方为空」的调账/外部转账，不是纯内部转账。
- **tab 污染**：DEG 全文删除 `\t`；更安全的做法是只对单号列/字段做 trim，避免破坏备注中的制表符。
- **商品名可含引号+换行**（`"foo""bar,\ntest"`），语法层必须正确处理 RFC 引号（现 `csv.ts` 已处理，保住）[ezB 测试]。
- **尾部空列**：微信导出常见 `,,,,`。当前 `csv.ts` 在行列数与表头列数不一致时直接判行错误，**P1 必须允许尾部空列**（按表头长度截断或忽略全空尾列），否则真实文件会整行报错。

### 4.3 京东金融

- header 签名「导出信息：」；数据表头首列 `交易时间` [ezB]
- **金额单位两套口径**：DEG 先剥 `(已退款x.xx)` / `(已全额退款)` 括号注记，再**删除所有 `.`** 并 `/100`（`1860` 与 `18.60` 都得到 18.60，`18.6` 会错成 1.86）；ezB 版本按元直接解析，括号注记同样存在。profile 用 `unitScale` 明确口径（1 或 100）。
- **列（ezB）**：`交易时间/商户名称/交易说明/金额/收/付款方式/交易状态/收/支/交易分类/备注`
- **列（DEG 固定下标）**：`[0]时间 [1]商户类型 [2]交易说明 [3]金额 [4]方式 [5]状态 [6]收/支 [7]交易分类 [8]交易订单号 [9]商家订单号 [10]备注`；**没有「商户名称」列**，不要混写。
- 状态白名单（ezB）：`交易成功/退款成功`；其他状态进 review，不整行丢弃。
- 「不计收支」子分支看交易说明：`充值`→对方=商户名称；`提现/转出`→账户=商户名称、对方=原账户；`转入`→对方=商户名称；`还款`→对方=商户名称；`退款` 或状态 `退款成功` → refund（ezB 用支出负金额，本插件用 `kind` + 正金额）；其他 → review [ezB]
- 商户名启发式：`京东平台商户` → 取交易说明首个空格分词且 <15 字符当对方，否则保留原串 [DEG]
- 行尾 `\t` trim [ezB]
- **跨渠道防重复记账**：`method: 微信-` → ignore 规则（微信账单里已有该笔）[DEG `example/jd/config.yaml`]

### 4.4 美团

- header 探测：表头行本身以「交易创建时间」开头；跳过后从下一行开始 [DEG]
- 金额：DEG 用 `array[7][2:]` 去掉 `¥`（半角 U+00A5 恰好 2 字节），对 `￥`/空格/其他符号不健壮；实现时用「剥非数字前后缀」而非定长切片。
- 收/支枚举：`支出 / 收入 / 不计收支`，未知本插件记 review（DEG provider 对未知类型返回 error）[DEG]
- 示例规则（`example/mt/config.yaml`）：`美团月付` → 负债账户；`美团余额` → 资产账户；`微信支付` → ignore（微信账单单独处理）。示例中**没有支付宝 ignore**，不要照抄成“支付宝也 ignore”。
- 可配置时间段：午餐 `10:30-14:00`、晚餐 `16:00-21:00`；同商户不在时间段内视为代金券。规则引擎需要 `timeRange`（见 §3.5）。

### 4.5 招商银行（借记 CSV + 信用卡 CSV 双模式，自动探测）

- **模式探测（逐行）**：首列 `记账日期` → 借记；首列 `交易日` 或匹配
  `((?:19|20)\d{2})年(0[1-9]|1[0-2])月` → 信用卡 [DEG `pkg/provider/cmb/util.go:92-110`]
- **借记**：表头
  `记账日期,货币,交易金额,联机余额,交易摘要,对手信息,客户摘要`；数据行判定 = 首格匹配
  `^(19|20)\d{2}-\d{2}-\d{2}$`；**可选列导致列序不固定，必须按真实表头重排**（DEG
  `fillDebitRow`，缺失列填空）；金额 `-` 前缀 →
  expense 否则 income；对手=对手信息、备注=客户摘要 [DEG]
- **信用卡**：表头
  `交易日,记账日,交易摘要,人民币金额,卡号末四位,交易地金额`；数据行判定 = 第 5 格 4 位数字；**日期只有 MM/DD**，年月从账单标题行提取；**跨年修正**：交易月份大于账单月份时年份减 1，即**标题 1 月 + 交易日 12 月 → 年-1**；**符号语义反转**：负金额（还款/退款）→
  income，正金额（消费）→ expense；金额去千分位 → 匹配前导数字 → **取绝对值**；
  `Peer` 固定 `CMB`、`Method` = 卡末四位，账户由 analyser/用户映射决定，**不要写“主账户固定信用卡”** [DEG]
- **日期-only**：借记日期没有时间，需用 `dateOnlyTime` 固定落点（建议 12:00 +08:00，避免 UTC 日历日漂移）。
- **身份**：招行没有稳定订单号；借记可用 `记账日期+金额+余额+对手`，信用卡可用 `交易日+金额+卡末四位+描述`，冲突时 review。
- ezB 未收录招行。

### 4.6 中信银行（信用卡 XLS）

- 跳 2 行标题；固定 8 列；列
  `交易日期/入账日期/交易描述/卡末四位/未使用/记账币种/记账金额/未使用`
- **只有日期无时间**；账单按**日期倒序**且同日无时间 → DEG 加 `(len-index)`
  纳秒 hack 恢复正序（我们用：稳定排序 + 保留行号次序即可）
- 方向：金额 `-` 前缀 → income（还款），否则 expense（信用卡语义，与借记相反！）[DEG]
- 对手固定 `CITIC`；示例配置用 `defaultCashAccount: Liabilities:CreditCard:CITIC`
  固定主账户，`财付通(银联云闪付) → ignore`，**`财付通还款 → Assets:WeChat`**（不是 ignore）
  [DEG `example/citic/credit/config.yaml`]
- **身份**：无流水号；用 `交易日+描述+金额+卡末四位` 复合键，重复风险高，冲突必须 review。
- ezB 未收录。

### 4.7 浦发银行（借记 XLS）

- **状态机探测**：行宽 > 3 且任一列出现 `交易日期/交易时间/交易摘要/交易金额`
  之一 → 表头，进入数据段；遇到含「合计」的行 → 终止（footer）[DEG
  `pkg/provider/spdb_debit/spdb_debit.go`，比跳行数健壮，照抄]
- 列（固定顺序）：`交易流水号/交易日期时间(2006/01/02 HH:mm:ss，可拆)/交易摘要/存入金额/支出金额/本次余额/对方户名/对方账号/附言`
- **存/支双列**：存入列非空且非 `0` → 负数 → income；支出列非空且非 `0` → 正数 → expense；两列皆空/0（如挂失费 0 金额）→ hardSkip；**金额列本身恒正**，方向由列位决定 [DEG]
- 空户名 → `Peer` 兜底 **`SPDB Debit`**（不是“浦发银行”）；时区 Asia/Shanghai；degenerate 行（外部转 internal 空金额）跳过 [DEG]
- **身份**：`交易流水号`（row[0]）可作稳定键；缺失时用 `日期+金额+余额+对方` 复合键。
- 该 provider **按固定列序**读取，不做表头重排；列序变化时由档案声明新的列序。

### 4.8 工商银行（借记 CSV，v1/v2 双态）

- **探测**：第 2 行「卡别名」；第 3 行「子账户类别: 活期」→ 借记模式，否则信用卡；跳过前 4 行；遇到「合计金额/人民币合计」结束 [DEG]
- **借记列数区分版本**：14 列 → v1，16 列 → v2；v2 多「交易说明」和「对方账号」。
  - v1：`[0]日期 [1]摘要 [2]对方 [3]地区 [8]收入 [9]支出 [10]币种 [11]余额 [12]对方户名`
  - v2：`[0]日期 [1]摘要 [2]交易说明 [3]对方 [4]地区 [9]收入 [10]支出 [11]币种 [12]余额 [13]对方户名 [14]对方账号`
- **信用卡**：`[1]日期 [2]摘要 [3]对方 [4]地区 [8]收入 [9]支出 [10]币种 [11]余额 [12]对方户名`。
- 表头金额带千分位逗号；**无借贷标志列**：两列皆空 → hardSkip（查询/无效行）；只有收入列有值 → income；否则（含两列皆有）→ **expense，取支出列**。不要写成“两列皆有 → unknown”。
- **身份**：无稳定订单号；用 `日期+金额+方向+余额+对方户名` 复合键，冲突 review。

### 4.9 兴业银行（借记 XLS/XLSX，多币种，支持多文件合并）

- 支持 XLS/XLSX 与**多文件合并**（`TranslateFiles`）。
- 头部键值扫描：`账户户名/账户账号/卡内账户`；**币种从「卡内账户」文字推断**（美元→USD/港币→HKD/人民币→CNY）[DEG]
- 表头行 = 首列「交易时间」；footer = 整行含「说明」即停 [DEG]（注意：数据行若含“说明”会被误停，需用列锚点而非单字包含）
- 列：`交易时间/记账日/支出/收入/余额/摘要/对方户名/对方银行/对方账号/用途/交易渠道/备注`
- **支/收双列各自支持正负双重语义**：支出列正→expense、负→income；收入列正→income、负→expense（负数是冲正）[DEG]
- 交易时间解析失败 → fallback 记账日 [DEG]
- 对方户名+银行+账号拼接为对手串 [DEG]
- **多币种购汇/结汇合并**（易漏）：同一账号、同一摘要（`购汇`/`结汇`）、不同币种、一出一进、时间差 ≤ 3 分钟时，合并为一条 `CurrencyExchange`，保留源/目标币种与金额；这是 DEG 的 `mergeCurrencyExchangeOrders`，实现按同账号+摘要+±3 分钟匹配并合并。
- **身份**：无稳定订单号；用 `交易时间+金额+余额+对方账号+摘要` 复合键；购汇合并后以「账号+时间+源币种/目标币种」为键。
- 注：DEG 本地 fork 无民生银行/华为钱包/PayPal/Steam/网易/真正的 OKEX（仅 OKLink 链上转账）；民生如需支持需从上游或自建档案。

### 4.10 随手记（三种文件：app CSV / web XLS / 随手云 XLSX）[ezB]

- **不是首行即表头**：app CSV 首行是文件头 `随手记导出文件(headers:v5;...)`，下一行才是表头；按列名读取，不要按固定列序。
- 列：`交易类型/日期/类别/子类别/账户/账户币种/金额/备注/关联Id/成员/项目/商家`（可选列缺省填空）。
- **app CSV 6 种交易类型**：`收入 / 支出 / 余额变更 / 负债变更 / 转入 / 转出`。
  - 余额变更：金额 ≥ 0 → income，< 0 → expense。
  - **负债变更符号反转**：金额 ≥ 0 → **expense**，< 0 → income。
  - 转入/转出：必须按 **`关联Id` 配对**；两条腿都存在才能合成一条 transfer，缺配对整份导入报错（`ErrFoundRecordNotHasRelatedRecord`）。
- **随手云/elecloud 额外类型**：`转账 / 借入 / 借出 / 收债 / 还债 / 代付 / 报销` → transfer；`退款` → expense。不要写成「债务变更/债权变更」。
- 日期：app 用 `YYYY-MM-DD HH:mm:ss`；elecloud 测试覆盖 `HH:mm:ss` / `HH:mm`（补 `:00`）/ 纯日期（补 `00:00:00`）。
- **身份**：转入/转出用 `关联Id` 配对；普通行无稳定单号，用 `日期+金额+账户+交易类型` 复合键。
- 此渠道是记账 app 间迁移（不是账单），列约束最规整，适合验证「列名完全已知」的最简路径；**放在 P4，不是 P2**。

### 4.11 建设银行 CCB（CSV / XLS / XLSX）

- **边界**：第 1 行含 `China Construction Bank`；第 2 行 `开户机构`；第 3 行 `币`；第 4 行 `账`（可取账号）；前 6 行说明；含「记账日」的行是表头；遇到「以上数据仅供参考」「具体内容请以柜台为准」结束；分页重复表头按「记账日」跳过 [DEG `pkg/provider/ccb/ccb.go`、`parse.go`]
- **列**：`记账日 / 交易日期 / [交易时间] / 支出 / 收入 / [余额] / 币种 / 摘要 / 对方账号 / 对方户名 / 交易地点`；**交易时间列可选**（用 `15:04:05` 探测），**余额列可选**（解析失败即视为缺失），后续字段按两个可选列的偏移读取。
- **方向**：
  - 支出 > 0 且收入 = 0 → expense；
  - 收入 > 0 且支出 = 0 → income；
  - 两者都 > 0 → 取净额（收入-支出）；净额为 0 时看摘要：含 `转账/转出` → expense，含 `转入` → income，否则默认 expense；
  - 两者都为 0 → 含 `查询/余额` → hardSkip（查询行）；含 `消费/支出` → expense 0；含 `收入/转入` → income 0；否则默认 expense 0。0 金额最终由 review 拦截。
- **日期**：`YYYYMMDD`，+08:00；有交易时间则拼接。
- **身份**：无稳定订单号；用 `交易日期+金额+余额+对方户名/账号` 复合键。
- 币种：按可选列偏移读取币种列；不要默认全部 CNY。源码头信息只保存账号，不从文件强制覆盖配置币种。

### 4.12 中国银行 BOC（借记 / 信用卡 CSV）

- **模式探测**：首个以「中国银行」开头的行作为文件头；行内含「信用卡」→ 信用卡，否则借记；之后跳 2 行 [DEG `pkg/provider/boc/boc.go`]
- **借记列**：`记账日期 / 记账时间 / 币别 / 金额 / 余额 / 交易名称 / 渠道 / 网点名称 / 附言 / 对方账户名 / 对方卡号 / 对方开户行 / 借记卡号`
  - 币别：`人民币` → CNY，否则 USD。
  - 金额：去负号后取绝对值；**负号 → expense**，正号 → income。
  - 日期时间：`YYYY-MM-DD HH:mm:ss`，+0800。
- **信用卡列**：`交易日 / 入账日 / 卡号后四位 / 交易描述 / 存入 / 支出 / 币种`
  - 存入为空 → expense（取支出列）；否则 income（取存入列）。
  - 源码把时间固定为 `20:00:00`（只有日期）；实现时用 `dateOnlyTime`，不要硬编码 20:00 作为业务语义。
- **身份**：无稳定订单号；用 `日期+金额+描述+卡后四位` 复合键。

### 4.13 农业银行 ABC 借记（CSV）

- 跳过表头；空首列行跳过；列：
  `交易日期 / 交易时间(HHMMSS) / 摘要 / 金额 / 余额 / 对方 / 日志号 / 渠道 / 附言` [DEG `pkg/provider/abc_debit`]
- **金额必须带显式符号**：`+` → income，`-` → expense；没有 `+/-` 直接报错，不猜测。
- 日期：`YYYYMMDD`（`20060102`）+0800；时间：`HHMMSS`，校验时分秒范围。
- 对手：为空或 `--` 时兜底 `ABC Debit`；交易说明 = 摘要 + 附言。
- **身份**：`日志号`（`LogNumber`）可作稳定键；缺失时用 `日期+金额+余额+对方`。

### 4.14 交通银行 BOCOM（借记 + 信用卡 CSV）

**借记**

- 跳过表头/空行；列：
  `流水号 / 交易日期 / 交易时间 / 交易类型 / 借贷标志 / 金额 / 余额 / 对方账号 / 对方户名 / 交易地点 / 摘要` [DEG `pkg/provider/bocom_debit/parse.go`]
- **方向由借贷标志决定**：含「贷」→ income，含「借」→ expense；金额本身无符号，不做正负推断。
- 日期：`YYYY-MM-DD` + `HH:mm:ss`，+0800；对手 = 对方户名 + 对方账号（拼接）。
- **身份**：`流水号`（可去掉 BOM）可作稳定键。

**信用卡**

- 首行首格 `交易日期` 为表头；列：
  `交易日期 / 记账日期 / 交易说明 / 交易币种/金额 / 入账币种/金额` [DEG `pkg/provider/bocom_credit`]
- 金额是「币种 + 金额」复合字符串（`CNY 12.34` 或 `CNY12.34`）；拆出币种，金额取绝对值。
- 交易说明首个空格前是交易类型：
  - 收入：`退货 / 信用卡还款 / 红包还款 / 刷卡金返还 / 自动购汇还款`
  - 支出：`消费 / 刷卡金扣回 / 分期扣款 / 自动购汇扣款`
  - 未知类型 → review（源码返回 error）
- 主金额/币种用**入账**币种金额；交易币种金额保留为 metadata。
- **身份**：无流水号；用 `交易日期+交易说明+入账金额+币种` 复合键。

### 4.15 广发银行信用卡（CSV）

- 来源是 `bill-file-converter` 从 PDF 转出的 CSV；首行首格 `交易日期`；列：
  `交易日期 / 入账日期 / 交易摘要 / 交易金额 / 交易货币 / 入账金额 / 入账货币` [DEG `pkg/provider/cgb_credit`]
- 日期 `YYYY/MM/DD`；金额带符号，**负数 → income（还款/退款），正数 → expense（消费）**；金额为 0 时看摘要类型：`退款/还款/入账` → income，`消费/分期/取现` → expense，否则 review。
- 摘要开头的 `（类型）` 或 `(类型)` 是交易类型；正则提取括号内文本。
- 币种归一化：`人民币/CNY/RMB → CNY`、`美元/USD → USD`、`日元/JPY → JPY`、`欧元/EUR → EUR`。
- 主金额/币种用**入账**金额/币种并取绝对值；交易金额/币种保留为 metadata。
- **身份**：无流水号；用 `交易日期+摘要+入账金额+币种` 复合键。

**覆盖范围**：DEG 本地 fork 已验证的银行 provider 包括建行、中行、工行、招行、中信、浦发、农行、交行、广发、兴业；未包含民生、平安、华夏、邮储等，按 §4.0 公共规则自建档案。

### 4.16 长期方向：声明式模板引擎（DEG v2 importer）

DEG fork 的 `pkg/importer` 已实现完全声明式的列映射引擎（YAML
`sourceHeaders`+`columns`+`when`
表达式+`postings`+在线 registry 模板版本 pin）。**建议仅作为远期路线（渠道数量 >10 后）**：届时手写 parser 的边际成本超过引入表达式引擎的复杂度。近期不抄（复杂度高，且 GUI 场景里「规则引擎 + 档案」已覆盖 90% 收益）。

## 5. 测试组织（golden 目录约定，抄 DEG）

每个渠道一个 golden 目录 `src/parsers/__golden__/<channel>/`：

- `input.csv` 或 `input.xlsx`：脱敏/合成样本（沿用现有 synthetic fixture 纪律）；
- `expected.json`：规范化后的 `StatementRow[]`（金额/日期/账户候选）；
- `rules.json`：账户映射规则（可选）。

`expected.json` 必须先规范化易变字段，否则换路径/环境就失败：

- `fileName` → 固定为 `<fixture>`；
- `lineNumber` → 固定为源文件物理行号；
- `date` → 固定为 `YYYY-MM-DDTHH:mm:ss+08:00`（或统一 UTC），并单独断言日历日；
- 账户候选只保留 `accountId/score/confidence`，不要包含账户显示名。

每个渠道表驱动跑「input → expected」，规则回归（ignore / min-max / 方向交换 / 退款 / 转账配对各一 case）；沿用环境变量门控的样本验收（`STATEMENT_DEMO_PATH`
模式复制为 per-channel：`WECHAT_DEMO_PATH`
等）。每渠道 4 类必备 case：正常消费 / 退款 / 关闭或非法行 / 转账类（不计收支分支树）。

银行渠道再加 6 类：**双列金额（含一列有值/两列都有/都为 0）**、**符号反转（credit vs debit）**、
**可选列缺失/列序变化**、**重复表头与页脚**、**日期-only + 跨年账单**、**多币种购汇合并**。
另外每个渠道至少一条「重复导入同一文件」用例，验证 `sourceKey` / 复合身份不重复。

## 7. 明确不抄的部分

- DEG 的 `log.Fatalf` / 未知交易类型直接 fatal（GUI 语境必须为可恢复的行级错误；未知业务值一律 review）
- DEG 的浮点金额（IR 用 `float64`，支付宝 provider 还用 32 位解析；现有字符串算术优于两者）
- DEG 跳行数硬编码（22/17/21 行），一律改签名/状态机探测
- DEG 的 FIXME 文本账户约定（GUI 用 review 分组 + 批量重指派）
- ezB 的自动创建账户/分类（宿主账户与分类归主程序所有，插件只做映射和选择；不要为此新增 `accounts.create` 权限）
- 用 `saveTransferPair` 创建模式去“补配对”已经存在的两条腿（会重复创建；应使用 `linkTransfer` 或传两个 leg ids 更新）
- 用负金额表达退款/收支方向（本插件用 `kind` + 正金额 + 宿主 activityType；负金额只作为解析中间量）
- ezB 无账单行级去重（它只有 `clientSessionId` 请求级防重提交；本插件保住四层去重，不要退化）
